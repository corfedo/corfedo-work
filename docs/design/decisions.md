# Decisions

## Taken

| Decision | Choice |
|---|---|
| Scope | Leases, reconciliation and jobs, plus chains, calendars and monitoring, so applications get the scheduling cases common .NET job schedulers offer from one framework. Dashboards, AI assistance, notification transports and stored handler log lines stay out. |
| Target frameworks | `net10.0` only. |
| Key codecs | `KeyCodec.Int32`, `Int64`, `Guid` and `String` cover keys of one field, also when a key type wraps the value. Composite keys implement `IKeyCodec` by hand. A codec defines a canonical string form that round-trips without loss and orders composite-key fields as declared. A generator is considered only once composite codecs are demonstrably repetitive. |
| Run history | Framework-owned storage with retention and read APIs; not pluggable. |
| Remote holders | Lease expiry alone decides that a holder is gone. An optional registry may later add visibility; it never affects validity. |
| Second provider | SQL Server, before the 0.2.0 release (owner): its local setup and proofs of concept of the primitives the PostgreSQL provider relies on (record and limit-scope locking, fences, merging, signals, the store clock) come before the provider. MongoDB challenges the contract before it is frozen. |
| SQL Server provider | `Microsoft.Data.SqlClient`, tests on `Testcontainers.MsSql`; SQL Server 2022 and 2025; the database must run with `READ_COMMITTED_SNAPSHOT ON`, refused at startup otherwise; signals through a framework signals table read below `MIN_ACTIVE_ROWVERSION()` (owner). Ids stay `uniqueidentifier` with the application's values; framework tables disable lock escalation and sources whose tables escalate are refused. Rejected: supporting databases without RCSI (claims wait for application writers and the limit-scope pattern deadlocks), Service Broker (not on Azure SQL Database, a queue per process, one `SEND` per process). See [SQL Server provider](sqlserver.md). |
| Cron parsing | [Cronos](https://github.com/HangfireIO/Cronos) (MIT) as a production dependency of `Corfedo.Work`, pinned to 0.13.0 (published 2026-04-29). The pin moves only after the cron scenarios (J-5, J-23, J-34) pass on the new version. Syntax and daylight-saving behaviour are Cronos's, without jitter; see [cron semantics](jobs.md#cron-semantics). |
| Dynamic group settlement | One pending count per group. It is revisited only if a measurement shows settlement throughput limiting a real workload. |
| Application-provided calendar dates | Published date sets with data revisions, stored by the framework, with a stated coverage end and at most one year of lookahead; uncovered dates hold planning instead of guessing. See [calendars](calendars.md#application-provided-dates). |
| Limit counting | Store-enforced limits count outstanding leases exactly in every claim (owner decision). PostgreSQL counts each partition once per claim statement from a partition index over outstanding leases and excludes saturated partitions with a hashed anti-join; the cost grows with concurrent leases (5 ms at 100k on 1M rows), not with the table. Per-scope counter rows are not used: `EndAsync` runs in the application's transaction, so a counter decrement would lock the scope until that transaction commits and serialize its claims behind it. |
| Claims in the caller's transaction | READ COMMITTED is required; other isolation levels are refused. Under snapshot isolation two claimers exceeded an owner limit of 1 in measurements; counter rows were rejected for the reason above. |
| Waiting for limit scopes | Framework transactions never wait for a limit scope while they hold record locks. Due claims do not wait for a busy scope at all: they skip its records, leave its partition out for the rest of the call and end the call when the owner's scope is busy, so one long application transaction does not stall other partitions or a pool's other sources. Exact limits only need the scope lock to be held when a claim is accepted. Claims by key wait for a busy scope at the start of their next attempt; claims in the caller's transaction wait for it. Waiting while holding record locks deadlocked with application transactions that claim in a scope and then write another of its records. |
| Settlement retries | Persisted per record (`SettleFailures`, `SettleRetryAt`) so every process honours the backoff; a failed settlement is not a failed attempt of the record. |
| Generation fence | A transaction-scoped advisory lock per supersede source: shared in fenced holder transactions, exclusive in invalidation, so guards that start while an invalidation waits queue behind it. A `FOR SHARE` lock on the generation row was rejected: on PostgreSQL 18.6 a new `FOR SHARE` was granted at once while an `UPDATE` waited for an earlier share locker, so overlapping guards could keep an invalidation waiting indefinitely. Claims take no generation lock: generations only grow, so an obsolete lease stays obsolete, and claims keep to the rule of never waiting while they hold record locks. |
| Requests during follow-up runs | A request during a run of a `FollowUp` source records its debounced due time on the record; the run's result schedules the follow-up from it. Leaving the due time alone would lose the request's debounce, which the result does not know. |
| Reconciliation executions | Derived, not stored: a name-based UUID (version 8, SHA-256) of the source, the canonical key, the claimed revision and the attempted generation, computed alike by every provider. Reconciliation records need no `ExecutionId` field, and the stores refuse `ScheduleAsync` on reconciliation sources altogether (see "Reconciliation lifecycle ownership"). |
| Reconciliation never gives up | `MaximumTakeovers` is refused on reconciliation sources; a failed run backs off by the lease policy's `FailureBackoff` and sets `NotBefore`, which ordinary requests respect. |
| Invalidation backlog | Claims alternate records due only by an invalidation with records due by time, one for one and across a process's claims of the source, so neither starves the other, also with one free slot. Stale records come from a non-partial index on `AttemptedGeneration` in index order: 0.05 ms per claim pass with 900k stale records out of 1M. |
| Pools | `AddPool(name, capacity)`; pooled sources do not set a capacity of their own. Free capacity goes to the highest priority class with claimable work first (a job definition's stored `Priority`; lease and reconciliation sources are `Normal`); within a class every pass starts with the next source and offers each an equal share of the free capacity, then the remainder to sources that used their share. C8 fairness holds within a class; lower classes may starve under sustained higher-priority demand, and capacity a higher class cannot use (limits, pause, incompatible versions) goes to lower classes. Priority never preempts. Ordering priority inside one source's claim statement was rejected: priority is per definition and each definition is its own source, so only the pool can order them. |
| Supersession reason | A hold whose renewal fails before its local deadline on a supersede source stops with `Superseded`; the store does not report why a renewal failed, since after a replacement claim supersession and takeover look alike. |
| Backoff floor and due time | On reconciliation sources `DueAt` is never earlier than `NotBefore`: requests store an earlier due time as the floor; schedules are refused on these sources. Next-due lookups stay on the `DueAt` index; including `NotBefore` there would scan every past-due record in backoff. |
| Reconciliation runs without a result | A claim whose hold ran out before its run started, and a run whose result could not be applied, are given back as failed lease releases (`Failures` + 1, due after the failure backoff, no `NotBefore`), not as `Failed`. No run produced a result, so no floor is set; the lease dispatcher stays independent of the reconciliation package. |
| Isolation of fenced holder writes | On superseding sources, guards, renewals in a transaction, completions and ends require READ COMMITTED and refuse other levels. The advisory fence orders them after an invalidation but does not refresh a snapshot, and invalidation writes no records, so a snapshot taken before it committed passed the generation check under REPEATABLE READ and SERIALIZABLE. Writing records on invalidation would give up C6. |
| Generation lock order | Generation fences come before row locks: fenced operations take the fence before their record lock, the `generation_fence` function takes several sources' locks in byte order of their keys, and transactions that commit holder output on supersede sources fence first with `GuardAsync` or `ReconcileOperations.FenceAsync`; invalidating transactions call `InvalidateAllAsync` before their own writes. A guard that locked its record before queuing behind an invalidation deadlocked with a fenced transaction writing that record. The order is a documented contract, not checked: a violation surfaces as a deadlock the store aborts. A refused fence raises an error, so a transaction that ignores it cannot commit. |
| Claim attempt budget | A due claim attempts at most twice its limit, claims and failed claim hooks or expiry handlers together. Up to limit failing records then do not reduce a call's claims, also with limit 1; a budget of exactly limit failures would make one failing record hide the next until polling. |
| Expiry processor wait | The expiry processor waits at most 750 ms between passes, idle or not, and its settlement scan is bounded by `now()` as well as checked with a fresh clock reading. Late-committed claims and locked records are not signalled; with the polling interval as the idle wait, settlement of such leases took up to 15 s, and a constant 250 ms retry while a record was locked cost 771 ms of database time per second for 100 processor loops behind 1000 locked leases. Measured on PostgreSQL 18.6: a lease committed, expired and unlocked was settled within 753 ms in idle, late-commit and overlapping-lock cases, at 123 ms of database time per second for those 100 loops. `NextExpiryAsync` is unchanged. |
| Next due after the claim's cutoff | A due claim returns its cutoff, the claim transaction's `now()` that bounds its scans, also when it claims nothing; `ILeaseStore.ClaimDueAsync` returns `DueClaims` and `NextDueAsync(source, cutoff)` counts unheld records due after the cutoff, expired leases whose takeover backoff ends after it and the next lease to expire, never negative, zero meaning claim again (owner decision). With `now()` at the lookup instead, a record that became claimable between the claim and the lookup was seen by neither, and the dispatcher waited the polling interval: on an AMD Ryzen 7 7700X with PostgreSQL 18.6, timers ended up to 0.9 ms early and 2 of 300 takeovers in a probe waited the full interval (L8). Rejected: a later `clock_timestamp()` as cutoff, which leaves records due between it and the scans' `now()`; counting everything already due, which spins on locked and limited records; a wake margin, which leaves passes started by signals or finished runs exposed. |
| Expiry settlement | One record per transaction, with the expiry handler in it; `NextExpiryAsync` unchanged. Settlement reads an index over unsettled leases, which settling sources must have: led by the stored generated column `LeaseOutstanding` and `LeaseExpiresAt` under `WHERE LeaseExpiresAt IS NOT NULL`, one shape for every store ([SQL Server provider](sqlserver.md), Outstanding leases), besides the index over all leases with an expiry that claims of expired leases use; job sources have it on `jobs`, led by the definition. Without it each settlement passed the expired leases already settled but not claimed again. Cost: 2.5 MB per 200k unsettled leases, no measurable write cost; selection 0.36 ms → 0.018 ms and one-process drain 939/s → 1406/s for a burst of 10k. Planner statistics must reflect that leases exist: with statistics from before any lease, PostgreSQL chose the partition index over outstanding leases for every settlement (3.3 ms) until autoanalyze ran. Reference performance (PostgreSQL 18.6 on an AMD Ryzen 7 7700X, no expiry handler work, current statistics), not limits the library enforces: settlement within one second of a lease becoming committed, expired and unlocked with 10 arrivals per second and clustered bursts of 100 per source, 1000 locked expired leases per source and 40 processor loops; recovery of 50 000 expired leases of one source within 150 s with one processor and within 45 s with four. Known limits: settling behind many locked expired leases scans past them on every pass (10 000 locked exceeded one second), and retries over locked leases add database load with the number of processor loops. |
| Claim selection with full partitions | Selection stays as it is: it leaves out saturated partitions with a hashed anti-join while reading the due index in order, so a pass in which every partition with due work is at its limit reads their queued records. Measured on PostgreSQL 18.6 with partition limit 2: 13.8 ms per pass with 100k records queued in 1000 full partitions, 135 ms with 900k in 10 000; 0.02 ms when no partition is full. A bounded probe, discovery by skip scan (about 5 µs per partition with due work), a process-local partition list and ready-partition metadata kept by a trigger with append-only hints were measured and deferred: each either slowed the common case, delayed newly due partitions, or added triggers on application tables, framework tables and their maintenance (the metadata variant: 0.9–8 ms per pass when every partition was full, insert cost +93 %, release +67 %). Revisited when a workload with full partitions and deep queues needs it. |
| Reconciler return type | `IReconciler` returns `ReconcileDisposition`: a `ReconcileResult` (implicit conversion) or `run.Completed`, which is not a result and so cannot be passed to `CompleteAsync`. A sentinel result was rejected: it was accepted as a failure by the completion APIs. Failed results the dispatcher applies are logged with their code. |
| Job records | Jobs are lease sources on the framework table `jobs`, one source `job:<key>` per definition, with the execution id stored on the record. Reconciliation sources were rejected: they derive the execution id from the claimed revision, so a request merged during an execution would change its identity. Every statement of a job source is scoped to its definition; eligibility (accepted argument versions, `MinimumArgsVersion`, pause) filters only claims and next-due lookups, so settlement, cancellation, retirement and outcome hooks also reach paused and incompatible jobs. Job sources always settle expiry. |
| Started executions and follow-ups | A job records that its execution started, separately from its attempt count, because a graceful release returns the attempt although external effects may have happened. Before the start a merging request replaces the arguments and merges the due time; after it, while the job runs or waits for a retry, the request becomes the pending follow-up and the execution keeps its arguments and execution id. Pending arguments: latest wins; pending due time: earliest wins, a debounce moves it later up to its maximum measured from the first pending request. The terminal transition records the outcome, runs the hook, then starts the follow-up with the same job id, a new execution id and fresh attempts. Cancelling discards the follow-up. |
| Job attempt accounting | Every claim that may run the handler uses an attempt; a graceful release returns it. A claim that finds the job late under `Late.SkipAfter` before its execution started, or no attempt left after a lost lease, uses none and writes no run-history entry: it ends the job skipped or failed with `attempts_exhausted` without a handler. `MaximumTakeovers` is not used on job sources; job exhaustion is the attempt budget. |
| Newest definition at claim time | A definition fence: a transaction-scoped advisory lock per definition, shared in every job claim before any record or scope lock, exclusive when a definition is stored or paused. After it the claim reads the stored revision and pause state; a claim built from another revision takes nothing and the dispatcher rebuilds its statements. Every claim therefore commits under the revision stored at its commit. Reading the definition before the claim without a lock was rejected: a newer revision could commit in between and an older worker would admit work under obsolete limits. A row lock (`FOR SHARE`) was rejected for the reason given under Generation fence. Transitions read policy from the stored definition inside their own statement. |
| Recurrences | Stored apart from job records in `job_recurrences`; each occurrence is a job record linked to its recurrence and unique per recurrence and occurrence identity. Planning is one short transaction per pass that locks due recurrences with `SKIP LOCKED`, plans with the store's clock reading and inserts occurrences idempotently; it takes no lease and never touches an execution's lease, and runs outside the execution capacity in every process that runs the definition's handler. Ended occurrences do not lock their recurrence; the planner consumes them. Of the ended occurrences only one planned from the current schedule advances an after-completion schedule; a triggered one releases only a waiting occurrence; a skipped or replaced-schedule one advances nothing. Retention keeps unconsumed occurrences. The recurrence handle is the definition plus subject or merge key; occurrences do not hold the standalone merge identity (see "Standalone jobs and recurrences"). |
| Standalone jobs and recurrences | Separate lifecycles, as in Temporal, Quartz.NET and Hangfire (owner). `RequestAsync` and `RequestManyAsync` create or merge standalone jobs only; merging, `IfAbsent` and follow-ups apply among standalone jobs of one identity, and a recurrence of that identity changes nothing about them. A recurrence owns its occurrences, which do not hold the standalone merge identity: overlap, waiting and after-completion spacing count only its own occurrences. `ScheduleAsync` never adopts a standalone job. Manual runs of a recurrence are explicit through `TriggerAsync`, which follows the overlap policy as a due instant does (under `Overlap.Wait` a trigger during a run records the waiting occurrence and returns `Waiting`). Occurrences have no follow-ups. A standalone job and an occurrence of the same subject may run at the same time; scheduled, manual and webhook work that must coalesce uses a dispatcher recurrence that requests standalone jobs. Partitions of standalone jobs and recurrences are independent. `CancelAsync` by subject cancels the subject's standalone jobs and its recurrence's outstanding occurrences; `RemoveAsync` deletes the recurrence and cancels its occurrences. Removed with the coupling: the identity fence (reruns of standalone jobs no longer meet recurrences; recurrence operations serialize on the recurrence row and its unique key), and the READ COMMITTED requirement of requests, completions in the caller's transaction and cancellations; claims and recurrence operations keep theirs. Reason: automatic adoption of independent work by a shared subject cost repeated design rounds (races with creation and removal, partitions, follow-up ids, isolation) for a guarantee the dispatcher pattern gives with the ordinary standalone rules. Behavior follows the established frameworks; edge cases are not designed beyond them. |
| Recurrence lock order | Recurrence operations (`ScheduleAsync`, `RemoveAsync`, `TriggerAsync`) lock the recurrence and then its outstanding occurrences; the planner locks recurrences with `SKIP LOCKED`, tries the definition fence, and waits for rows and index entries at most a short `lock_timeout` (50 ms), leaving a recurrence it cannot plan for its next pass. The planner runs no outcome hook (owner decision), so a transaction that waits for it never waits for application code; recurrence operations are documented to come before the transaction's own writes, but the planner no longer depends on it. Locking the recurrence from an occurrence's terminal transition stays rejected: that transition runs in domain transactions holding domain locks. |
| Recurrence operation isolation | Recurrence operations in the caller's transaction (`ScheduleAsync`, `RemoveAsync`, `TriggerAsync`) require the store's read-committed isolation where it has one and refuse other levels with `InvalidOperationException` before any lock or write, as claims in the caller's transaction do (owner approval). Reproduced on PostgreSQL 18.6 with a REPEATABLE READ caller transaction that read before a concurrent request committed: the schedule created the recurrence without adopting the committed job, the removal deleted the recurrence and left its committed occurrence outstanding, and the trigger failed on `jobs_merge`; under READ COMMITTED the job was adopted, cancelled and made due. With separate lifecycles the requirement stays for the occurrences these operations find after their locks, which the planner may have committed after the transaction began. Rejected: switching the caller's isolation level or retrying its transaction internally. |
| Requests racing recurrence creation | Superseded by "Standalone jobs and recurrences" (owner): with separate lifecycles a request never joins a recurrence, so there is no race to coordinate. The implemented coordination (terminal adoption, `jobs.adoption_ended_at`, partition records and keys, request fence probes, `JobRequestConflictException`, READ COMMITTED for requests, completions and cancellations) is removed. |
| Skipped occurrences | The planning transaction records an occurrence the overlap policy skips as a durable "to be skipped" job (`skip_pending`, no due time, never claimable, no attempt) and advances its cursor; a separate transaction per occurrence ends it skipped (reason `overlap`) through the terminal path with its outcome hook, holding no recurrence lock, also while paused and after the recurrence was removed (owner decision). A crash or a failing hook leaves the record outstanding for a later pass. This replaces committing skipped outcomes and hooks in the planning transaction, whose hooks could wait for domain locks while the planner held a recurrence. |
| Requests against a recurring job's identity | Superseded by "Standalone jobs and recurrences" (owner): requests no longer route into recurrences; requested occurrences, folding instants into them, the planned instant capping a debounce, adoption by `ScheduleAsync` and follow-ups of occurrences are removed. `RequestAsync` and `RequestManyAsync` still take one-shot schedules only, and recurrences are created and replaced with `ScheduleAsync`. |
| Subject pause | The stored pause (`job_pauses`) is the authority claims check (owner decision). Pausing and resuming a subject take a transaction-scoped advisory lock per definition and subject exclusively; claims try it in shared mode for each locked candidate after the definition fence and their row locks, skip a busy subject, and then check the stored pause in a new READ COMMITTED statement, so a pause waits for claims in flight and later claims see it. Requests take no pause lock; they copy the pause into a `paused` flag that keeps paused jobs out of the due index, and maintenance repairs stale flags in both directions, so a job flagged by a request that raced a resume becomes claimable at the next repair pass without further requests. A claim pass takes at most one subject lock per record it locked (up to its limit per scan: one scan per accepted argument version, the expiry scan and, with an owner limit, the owner scan). Rejected: a per-subject lock taken by requests. With default settings (`max_locks_per_transaction` 64, `max_connections` 100) one transaction held 14 000 advisory locks and failed at 17 000 with `out of shared memory`, so fan-out of 50 000 subjects could not work; and a request after a domain write deadlocked with a pause that then wrote the same domain row (reproduced on PostgreSQL 18.6). The flag and its repair are described under "Copied pause flags and their repair". |
| Copied pause flags and their repair | `job_pauses` stays the authority and the claim locking stays as it is; jobs and recurrences carry a copied `paused` flag that keeps paused work out of the due indexes (owner decision). Pause and resume update the subject's existing recurrences and then its jobs at once, the lock order of recurrence operations. Requests, schedules and planning inserts copy the stored pause without a lock; a copy left stale by one that raced a pause or resume is ignored by claims and planning, which read `job_pauses`, and corrected by a later successful maintenance pass, which reconciles both directions for recurrences and jobs with bounded updates and `SKIP LOCKED` and signals planners and claimers when clearing flags releases work. The `LIMIT` bounds the rows repaired, not the rows read, so total cost follows the maintenance frequency and the number of processes: on PostgreSQL 18.6, with 100 000 flagged jobs and one flagged recurrence per paused subject, a pass that finds nothing stale takes 43 ms at 1 000 paused subjects and 97–104 ms at 50 000 and 100 000. Clearing reads its candidates in a materialized anti join, 36 ms for jobs at 100 000 against 254 ms with one `job_pauses` probe per flagged job under the `LIMIT`. The flags keep the claim due scan at 0.08–0.12 ms, against 150 ms without, and the planner's due selection and next wake at 6.2 ms and 0.03 ms with 50 000 paused overdue recurrences, against 97 ms and 90 ms. Rejected: a pending-repair table with generations and a transaction-id drain, which would let maintenance forget a changed subject but needed READ COMMITTED for every flag writer and a delicate proof (several variants reproduced as wrong); taking a row lock on `job_pauses` plus a subject advisory lock in requests, which ties large fan-outs to the shared lock table and adds deadlocks with application transactions; a recursive loose index scan over flagged subjects, 5.5 ms at 1 000 subjects but 2 s at 100 000; repairing only stale `true` flags, since stale `false` flags from a fan-out that raced a pause keep paused jobs in the due index for the whole pause; no copy, which reads every paused due job on every claim pass. |
| Missed occurrences | When the planner handles a recurrence, one instant due since the last planned one is planned and `Late` decides at its claim; several are missed: `Missed.Skip` plans none and continues from the next future instant, `Missed.RunLatest` plans the latest. Planner delay, downtime and pause use the same rule; `Missed` applies first, then the overlap policy, then `Late` when the occurrence is claimed. A separate misfire threshold was rejected as a second lateness setting beside `Late`. Occurrences already created keep their own lifecycle. |
| Job version filter | Claims and next-due lookups read unheld due jobs with one range per accepted argument version on an index led by definition, argument version and due time. One range over `(definition, due_at)` with the version as a filter read every due job of an unaccepted version first: 16 ms for the due scan with 12 500 such jobs due before the accepted ones, against 0.56 ms and 0.03 ms for the two per-version scans, on 1M rows on PostgreSQL 18.6. Candidates of all ranges are evaluated together in due-time order. |
| Follow-up lateness | A follow-up keeps its pending due time and `Late.SkipAfter` measures lateness from it, so the follow-up of an execution longer than the grace may end skipped at its first claim, with no attempt and through the outcome hook. Definitions whose follow-ups must run regardless use `Late.Run`. |
| Jobs without a partition | Share one default partition per definition across processes, limited by `PartitionLimit` like a named partition; `DefinitionLimit` covers the whole definition. |
| Cancellation at a recovery claim | A cancellation requested while a holder ran the job takes precedence over lateness and exhaustion at the next claim: the job ends cancelled without a handler or an attempt. Checking exhaustion first ended a cancelled job failed when its last attempt's holder crashed. |
| Requests into a claimed execution | A merging request becomes the pending follow-up when the execution started or a claim took the job's lease, not only when it started. A claim that ends an unstarted job skipped under `Late` would otherwise end it with the request's arguments. The condition does not depend on the clock, so the outcome a request reports matches what it wrote. |
| Job results | A definition with a result type is `JobDefinition<TArgs, TResult>`, derived from `JobDefinition<TArgs>`, whose results are serialized with the host's JSON options (see "Job JSON") or a result codec `IJobResults<TResult>` (`Version`, `Write`, `Read(data, version)`; `JobResults.Json(typeInfo, version)`) given to the definition; the version is stored with the result (owner decision). Its handler is `IJobHandler<TArgs, TResult>` returning `JobDisposition<TResult>`, which converts from a `TResult` (completed with that result) and from a `JobResult`; `JobRun<TResult>.CompleteAsync(tx, value)` completes in the domain transaction. `JobResult.Completed` from a typed handler completes without a result. A serialized result holds at most `JobResults.MaximumBytes` (256 KiB): a larger one returned to the dispatcher ends the job failed with `result_too_large`, since retrying cannot help, and `CompleteAsync` refuses it before writing. The result is stored with the outcome in the terminal transaction. |
| Result versions | Results are not routed by version (owner decision): result codecs read every version their definition has written, and new result versions are deployed readers first; a read of a result newer than the reading codec throws `JobResultVersionException` before decoding, which fails a handler's attempt with `result_version`. A result is newer than its reader only during a rolling deployment, unlike arguments, which wait across deployments. Rejected: recording each step's input versions and filtering claims on them (`AcceptsParentResults`), since a group continuation reads several definitions' results, so exact routing needs a (definition, version) key in `jobs_due` whose claim ranges grow with the combinations, and a residual filter read 12 500 unaccepted rows to claim 32 at 1M jobs (1.9 ms against 0.18 ms). |
| Status by subject | `GetAsync(definition, subject)` returns `JobStatus` or null when the subject has no job, recurrence or ended job; `GetManyAsync` reads at most 1 000 subjects per call and leaves out subjects with nothing (owner decision). `JobStatus` has `State` (`Scheduled`, `Running`, `Idle`), the job, due time, running since, occurrence, attempt, progress, the last outcome with reason and end time, the recurrence's next occurrence, `Paused` (definition or subject) and `FollowUpPending`. It describes the subject's running job, otherwise its earliest-due outstanding one, standalone job or occurrence. Reads are by subject only. |
| Outcomes and waiting | `GetOutcomeAsync(definition, jobId)` returns the latest ended execution of the job id with its `ExecutionId`, outcome, reason, end time and, for typed definitions, `HasResult` and `Result` (`JobOutcomeStatus` / `JobOutcomeStatus<TResult>`); `Ended` is false while an execution of the id is outstanding, including a one-shot follow-up that reuses it; null for an unknown id (owner decision). `WaitAsync(definition, jobId, timeout)` returns once the id has no outstanding execution and returns the same record with `Ended` false at the timeout. Recurring follow-ups have job ids of their own. Only jobs a caller waits for signal their end (owner decision): `WaitAsync` marks the outstanding job with a shared boolean (`jobs.waited`) in a plain update that takes no lease and skips a job already marked (`AND NOT waited`), and the transition that leaves the job without an outstanding execution clears it and sends a per-definition `Ended` signal in the same transaction; retries and a follow-up reusing the id keep it, and a waiter that times out or is cancelled leaves it for the others, so a mark left behind causes at most one later signal. One waiter per process listens from the first wait; a waiter marks its job only once listening and rereads it after the mark committed, so a completion is either read or signalled. It rereads the waited ids of a signalled definition in one statement, all of them on reconnect and every second as a fallback. Rejected: an `Ended` signal on every terminal transition, since any notification serializes the commits of notifying transactions (PostgreSQL 18.6, 8 committers: 16 300 → 4 040 terminal transactions per second, a second notification in the same transaction free); polling alone, which returns up to a second late. |
| Progress | `run.ReportProgressAsync(percent, message)`: a whole percentage 0–100 and a message of at most 256 characters, written in its own transaction fenced to the attempt's lease (`LeaseLostException` when stale) and cleared by every claim that runs the handler (owner decision). |
| Run history entries | Enabled per definition by `JobPolicy.RunHistory`, stored policy in the digest and disabled by default, since entries are written by whichever process ends, settles or takes over an attempt (owner decision). One entry per attempt in `job_runs`, keyed by job and epoch, inserted when the attempt ends: on the terminal path, a retry, a release while the lease is valid (`Released` when graceful, which returns the attempt; `LeaseLost` when failed, which follows a lost hold, ended at the release; owner decision), expiry settlement, or a claim that takes over the lost lease (including late, exhausted and cancelled claims, which create no entry of their own). The start comes from the attempt's start on the job record, so a running attempt appears in `JobStatus`, not in the history. `JobRunOutcome`: `Completed`, `Failed`, `Cancelled`, `TimedOut`, `Skipped`, `Retried`, `LeaseLost`, `Released`. `GetRunsAsync(definition, subject | jobId, limit, after)` returns entries newest first with a keyset cursor on start, job and epoch; default limit 50, at most 1 000. Retention is separate. |
| Job lifecycle ownership | Job handlers get `JobRun` without its lease run: identities, attempt metadata, `Owner`, cancellation with `StopReason`, `GuardAsync`, progress and completion (owner decision). `LeaseOperations` refuses claims, releases, ends, schedules and cancellation requests on job sources, also for leases parsed from tokens, since they bypassed outcomes, hooks, results, run history, wait signals and attempt accounting (a lease end left the job outstanding and never due); renewals and guards remain. Dispatchers claim and release through the store. |
| Reconciliation lifecycle ownership | Reconcilers get `ReconcileRun` without its lease run: key, partition, revision, generation, identities, `Owner`, claim `Reason`, cancellation with `StopReason`, `GuardAsync`, `RenewAsync` and `CompleteAsync`. The reconciliation layer owns `DueAt` on its sources: `LeaseOperations` refuses releases, ends and schedules on them, also for leases parsed from tokens, and both stores refuse schedules on them with `ArgumentException`, since a release or schedule without a due time and a lease end dropped a claimed revision or a pending request until the next request or invalidation (owner). Claims, renewals, guards and cancellation requests remain; a holder gives a record back with a result through `ReconcileOperations.CompleteAsync`. Dispatchers release through the store. |
| Stage 4 scope | Jobs with the process registry and its reports (R12, R21, J10); lease validity never depends on the registry. Application isolation (R19), `StartMode.Manual`, calendars, chains, monitoring and the chain part of J-24 are later stages. |
| Reruns (4d) | `RerunAsync` keeps the job id and starts a new execution id with fresh attempts on the same row; it is refused atomically while any execution of the job is outstanding (scheduled, running or retrying) or while another outstanding standalone job holds its merge identity, and never queues a follow-up (owner decision). Lease epochs are never reset on a reused row, so run history entries stay distinct and old lease tokens stay invalid. Shape: `RerunAsync(definition, jobId)` and `RerunManyAsync(definition, jobIds)` run in the store's own transactions and return `RerunResult(Job, Outcome)` per id in order: `Rerun`, `Outstanding`, `IdentityHeld`, `Recurring`, `Duplicate`, `NotFound`. Occurrences are refused as `Recurring`: rerunning an occurrence row would end it unconsumed again and could advance its schedule twice; `RunNowAsync` and `TriggerAsync` run recurrences (owner accepted, with the same job id, a new execution id, fresh attempts and monotonically increasing lease epochs). Reruns take no identity fence: with separate lifecycles a standalone job never meets a recurrence (owner). The ended execution's outcome and result stay readable with `Ended` false until the rerun ends, as for a follow-up that reuses the id. |
| Run now (4d) | `RunNowAsync` never throws for a job's state: in one locked update it moves the due time of an outstanding, unheld, ungated job to now and reports what it found (owner decision). A job scheduled later or waiting for a retry backoff becomes due now with its attempts kept (`MadeDue`); a paused one also becomes due now and is reported `Paused`, running once resumed; an already due one is `AlreadyDue`; a held one is `AlreadyRunning` and nothing is queued; a follow-up gated on an occurrence that has not ended is `Waiting` and keeps its gate; a terminal one is `Ended` (rerun it with `RerunAsync`); an unknown id is `NotFound`. A recurring job is triggered, with the trigger's outcomes, under the same result shape. Rejected: refusing already due or running jobs, which turns repeated operator calls and races into errors; queuing a follow-up for a running job, rejected for reruns for the same reason. Shape: `RunNowAsync(definition, jobId)` runs in the store's own transaction and returns `RunNowResult(Job, Outcome)`, which replaces `TriggerResult` and is also what `TriggerAsync` returns (`Started`, `MadeDue`, `AlreadyRunning`). An outstanding occurrence is evaluated like a one-shot job under the recurrence's lock order; an ended occurrence, or one waiting to be recorded skipped, triggers its recurrence, and `Started` names the new occurrence. A lost lease waiting for its takeover is `AlreadyDue`; an occurrence waiting to be recorded skipped is `Waiting` and triggers nothing, although the identity lock excludes it. |
| Retention (4d) | Separate retention durations for terminal jobs and for run history, stored per definition with its policy and revision; host configuration supplies defaults, workers apply the stored policy (owner decision). Starting defaults: 7 days for terminal jobs, 30 days for history; product defaults, not measured requirements. The latest outcome of a subject is retained finitely like any other; after retention `GetOutcomeAsync` returns null as for an unknown id, and applications that need durable outcomes persist them through the outcome hook. Retention deletes only terminal jobs (selected by state, since restarted follow-ups keep `ended_at`), keeps unconsumed occurrences and jobs referenced by `after_job` or a recurrence's awaited job, covers records without a subject, and runs as a recurring job the hosting package provides. Shape: `JobPolicy.Retention` and `JobPolicy.RunHistoryRetention`, null for the host default; the declared values are in the digest and the resolved ones are stored with the revision, so a changed host default (`WorkBuilder.Retention(jobs, runHistory)`, `JobRetention` in the store's `StoreDefinitionAsync`) applies from a definition's next revision instead of failing startup with a digest conflict. Running retention is an explicit opt-in (owner decision): `work.AddRetention()` registers the job `WorkRetention.Definition` with its handler and an hourly fixed-rate recurrence, while `Retention(jobs, runHistory)` only sets the default durations. Request-only processes stay dispatcher-free, as an API that enqueues jobs while worker deployments run handlers and maintenance; at least one worker deployment per shared store and application opts in, and several replicas may, coordinating through the job's lease. Registering it in every `AddWork` process was rejected for that reason. The job it deletes per definition in batches of 1 000, one statement per transaction with `SKIP LOCKED`, until a pass fills no batch. Indexes `jobs_retention (definition, ended_at) WHERE state <> 0` and `job_runs_retention (definition, ended_at)`: 9 ms per batch of 1 000 at 1M jobs and 2M entries against 508 ms and 322 ms without them (see [providers](providers.md#postgresql)). |
| Process registry (4e) | Heartbeat every 15 s, stale after 60 s, both configurable and evaluated with the database clock; staleness affects reports only, never lease validity (owner decision). Reports of unserved definitions and versions, undeclared recurrences and outdated processes are structured framework read APIs; dashboards and alerting stay outside 4e. Stopped processes are kept 7 days after stopping, abandoned ones 7 days after becoming stale, and then deleted by the next starting process (see "Process registry layer"). |
| Pause flag set after a resume | A request, schedule, planner insert or rerun that races `ResumeAsync` copies the pause flag from `job_pauses` without a lock and can store `paused = true` for a resumed subject. The copied flag with two-way repair stays (owner decision): work hit by the race runs after the next maintenance pass of a running worker of its definition, at most about one polling interval later, and is never lost, since only such a worker can run it. The unserved report is not affected by stale flags (owner decision): for a definition no live process runs, and only when it has no other due work, the report reads the subjects of its flagged due jobs and recurrences against `job_pauses`, a merge over indexes ordered by subject (80 ms in the worst case of 100 000 paused subjects, 1.6 ms on the registry dataset); a definition a live process runs has its flags repaired by that process. Measured and rejected replacements for the copied flag are under "Rejected designs for the pause flag race" in [providers](providers.md): copying under `FOR KEY SHARE` on the pause row (resumes wait for application transactions; schedule/resume and multi-subject resume/fan-out deadlocks) and a conservative flag set only by pausing and maintenance (under sustained paused arrivals active claim p99 324 → 2 520 ms, arrivals 997 → 576/s, growing backlog). |
| Process registry layer (4e) | The registry is its own layer, usable without other work for an inventory of process instances, such as two live `control-plane` replicas (owner decision). It records one type per instance, by default the host's application name, and an optional release; there are no roles. It registers, heartbeats, marks stopped, lists by type and state (live, stale, stopped) and keeps records 7 days after stopping or becoming stale. The instance id is the lease owner id. A process that adds work registers when it describes itself with `work.Process(...)`, runs a handler or declares a code-defined recurrence; processes that only request work are not recorded. The job definitions of a registered process (revision of its own code, runs, accepted argument versions, recurrence declaration) and the coverage reports belong to Jobs (`JobOperations.GetUnservedAsync`, `GetUndeclaredRecurrencesAsync`, `GetOutdatedProcessesAsync`). Reports are existence checks without counts or due times, change no record and never match jobs to recurrences. Due work is an unheld due job, an expired lease or a recurrence its planner would act on now; paused definitions and subjects are left out by the stored pauses. Every starting process deletes, in batches of 1 000, the records that stopped or became stale more than 7 days ago (owner decision): records are only added at a start, so the registry stays at about one week of starts without a schedule, with or without `AddRetention()`; a record goes at the first start after its 7 days. Metadata, endpoints, health probes, routing and leader election are out of scope. |
| Statement preparation | Measured before any setting is chosen: claims, renewals and the terminal statement through Npgsql with pooled connections and realistic definitions; application-controlled auto-prepare on the supplied data source is preferred over provider-managed preparation (owner decision). PostgreSQL can still choose custom plans for prepared statements, and Npgsql tracks prepared statements per physical connection. The run history CTE stays as it is. |
| JIT on large statements | Only the unserved report turns JIT off for itself, with `set_config('jit', 'off', true)` in its batch; no other statement switches it and the framework changes no server setting (owner). Measured at 1M and 10M jobs, every other statement stays below `jit_above_cost` in normal operation. Two cross in edge cases where JIT changes little: a claim pass that leaves out a busy partition holding most of a definition's due jobs (61 ms without JIT, 150 ms with it at 10M; the scan of that backlog is the cost) and a `RequestManyAsync` fan-out of more than about 12 000 items (1–7% slower). Adding the switch to every claim pass measured no difference, so it brings nothing on the normal path. See [providers](providers.md). |
| Calendar coverage reporting | Date sets are reported ahead of need, not only once work stalls (owner). A `JobOperations` read API lists per date set its coverage end, the calendars using it and a state: covered, running out (coverage ends within a configurable margin, default 30 days, of the instants planning needs) or work waiting (jobs held for uncovered dates). Maintenance logs only state changes (running out, work waiting, covered again), never once per pass. Stage 5c adds a built-in expectation that date sets stay covered, delivered as incidents. Rejected: a `JobStatus` state only, which misses jobs without a subject and gives no system-wide view; a warning logged every pass. Shape: the read API is `CalendarOperations.GetDateSetCoverageAsync()`, next to publishing and removal, and returns `DateSetCoverage(Name, Revision, CoversThrough, Calendars, State)`, also for sets a stored calendar uses before they are published (revision and coverage null, running out); the margin is `work.CalendarCoverage(margin)`, compared by UTC days. The instants planning needs are now, outstanding jobs' instants still to be planned and recurrences' next instants within the one-year lookahead; planned due times are not, since they are already decided. Work waiting is attributed to the unpublished sets of a waiting calendar, otherwise to its sets covering the fewest dates, since planning stops at the first uncovered date. Every process that registers a calendar reads the report at the polling interval and logs `calendar.date_set_running_out`, `calendar.work_waiting` and `calendar.date_set_covered` on changes from the state it last saw, covered at start. |
| Calendar removal | Removal is a hard block, never a soft delete, while live work uses the calendar: outstanding jobs, recurrences or a stored calendar composing with it (owner). Finished jobs do not block: the terminal transition moves the job's calendar reference to a column without a foreign key, and a rerun of a finished job whose calendar was removed is refused as `RerunOutcome.CalendarRemoved`. The refusal names what blocks it. A report lists stored calendars that no live process registers, like undeclared recurrences. Rejected: a foreign key from every job, which blocked removal until retention deleted finished jobs, beyond the design's "referenced by a stored schedule". Shape: `CalendarOperations.RemoveAsync(name)` throws `InvalidOperationException` naming the outstanding jobs counted per definition, the number of recurrences and the composing calendars; the rerun's restore of the reference hits the foreign key atomically, so a removal and a rerun cannot both succeed. Stored calendars no live process registers are listed by `CalendarOperations.GetUnregisteredCalendarsAsync()`, from the calendars recorded per registered process; a process that registers a calendar is recorded in the process registry. |
| Calendar planning | A job with a calendar is stored with its requested instant and no due time, out of the due index, and the definition's maintenance plans it when the instant comes: an allowed instant becomes the due time with the end of its window; a blocked one is moved forward, or recorded skipped with `calendar_blocked` under `Blocked.Skip` or `Reject` and always for occurrences; one needing uncovered dates waits until a covering revision is published; one with no allowed instant within one year is skipped. One planning path serves requests, occurrences, retries, follow-ups and operator actions, and date-set revisions published before the instant apply without re-planning. Retries, `Closed.Wait`, operator actions and released waiting occurrences plan with move-forward. Calendars are evaluated in .NET (`TimeZoneInfo`, no dependency) with the store's clock against the stored calendars and date sets read in the planning transaction; a spring-gap local time maps to the end of the gap, an autumn-overlap one to its first instance, and equal window start and end allow a full day from the start. Rejected: evaluating calendars in SQL, which would duplicate the evaluator per provider. |
| Calendar windows and claims | Claims require `window_end` after the claim time only for unheld jobs; a takeover of a lost lease is not held to the window, as a running attempt continues past it. Work whose window closed before it started keeps its due time with a new window end when the calendar allows the current instant, otherwise follows `Closed`; this also applies to an instant moved forward to a window that already closed, for example when the planner ran late. Work an operator made due with `IgnoreCalendar` gets an endless window, so a later date-set publish does not plan it again; its retries respect the calendar. |
| Calendar requests and merging | `Blocked.Reject` is checked when the request is made, with the stored calendars and date sets; an uncovered instant is refused as unavailable, and an accepted instant found blocked later ends skipped. A request that merges before the job starts replaces its calendar and policies, latest wins, and merges the instant; one that becomes the follow-up keeps the job's calendar. A standalone job recorded skipped by its calendar takes requests as follow-ups, which start when it ends. An occurrence skipped by its calendar stays unconsumed so after-completion schedules advance; overlap skips stay consumed. A declared recurrence's digest includes the calendar and closed policy only when it has a calendar. |
| Calendar type name | The public calendar type is `WorkCalendar` (owner): `Calendar` clashes with `System.Globalization.Calendar` in every file importing `System.Globalization`. The other calendar types keep their names (`CalendarDates`, `CalendarSlot`, `CalendarEvaluator`, `CalendarOperations`, `ICalendarStore`), as do `AddCalendar` and `Within`. Rejected: keeping `Calendar` with a documented alias. |
| Chain storage | Every chain step is a `jobs` row from the moment the chain is requested, with chain columns, and waits for its parent without a due time, outside the due indexes; `job_chains` and `job_chain_groups` hold the chain and its groups with one pending count and the worst outcome each (owner). Waiting for the parent is a job status, `WaitingForParent`, with one rule per operation: run-now, trigger and rerun refuse chain steps, cancellation ends a waiting step cancelled and its children follow their conditions, pauses, calendar removal and argument-version retirement treat it as any outstanding job. Claims, their indexes and requests are unchanged. Rejected: a step table that inserts a step's `jobs` row only when it becomes due, which copies every request column and its validation, doubles the writes of a fan-out and leaves skipped steps without the outcome hook; a waiting step detected only from a missing due time, with refusals added per operation. |
| Chain settlement | A step's terminal transition decides its children after the outcome hook: those whose condition holds become due, the others are recorded with `skip_pending` and `chain_condition` and ended by their own definition's maintenance, as calendar and overlap skips are, so only a process that registers a definition runs its outcome hook. A group has no condition: each branch's first step waits for the group's step with its own condition, so one `UPDATE` decides every child of a settled step, and a group whose branches were all skipped settles skipped. A skipped root marks every waiting step `root_skipped`, whatever its condition. A group continuation reads the results of the steps that end the group's branches. `ChainDelete.Cascade` cancels the steps and the transaction that settles the chain deletes it. Rejected: ending skipped children in the parent's transaction, which would run the outcome hooks of definitions the settling process may not register. |
| Recurring chain occurrences | An occurrence of a recurring chain has no handler of its own: when it runs it creates its chain, gives up its lease and waits without a due time, its attempt open and held by the chain, until its definition's maintenance ends it with the chain's outcome and a `chain_failed`, `chain_cancelled` or `chain_skipped` reason. Running is defined once, as a valid lease or an attempt its chain holds, for status, run-now, triggers, overlap and monitoring, and the attempt's run history entry spans the chain with the chain's outcome (owner). An occurrence skipped before it runs creates no chain. Cancelling the occurrence cancels its chain in the same transaction and leaves the occurrence running until the chain settled, when it ends with `chain_cancelled` (owner decision), so overlap, monitoring and the run history entry still span the chain; retrying the chain does not reopen the occurrence. Rejected: creating the chain when the occurrence is planned, which would create chains for occurrences the overlap policy skips; ending the occurrence at once and leaving its chain running, which let the next occurrence start a second chain beside it; refusing the cancellation while a chain runs. |
| Cancellation lock order | Cancellations take every step lock before they end anything: outstanding jobs first, then steps waiting for their parent, each in id order. A cancellation by subject or merge key also locks the waiting steps of the chains of the jobs it selected, since ending a step decides its waiting children and the continuations of the groups it settles, and step ids follow no order within a chain; a chain cancellation locks all of the chain's outstanding steps. Rejected: ordering step ids by their place in the chain, which a dynamic group added by another process's clock or ids created in one millisecond cannot guarantee. |
| Application isolation | Each application sharing a database has its own framework schema (owner decision): the PostgreSQL store already derives tables, advisory-lock keys and its signal channel from its schema, so R19 needs no change to statements, and `Application(name)` is not part of the registration. Rejected: an `application` column in every framework table, key and claim; it measured no claim cost (a 32-job due scan at 1M jobs, 0.060–0.063 ms with the column leading `jobs_due` against 0.080–0.082 ms), but changes the keys of 14 tables and every statement for no requirement that a schema per application does not meet. |
| Retry of dynamic groups | Retrying from a step that added a dynamic group deletes that group with its steps and groups, and the step adds it again when it reruns; retrying from the dynamic group or a step inside it keeps the group. Groups record whether a running step added them (`dynamic`). Rejected: resetting the added group with the step, which runs its branches twice once the step adds its group again. |
| Chain retention | A chain is retained as a unit for the owner definition's `job_retention` when an occurrence owns it, otherwise for the longest `job_retention` of the definitions of its steps, from its settlement and with the settings current when retention runs (owner). Per-definition job retention skips chain steps. Rejected: the root step's definition only, which deletes steps of other definitions before their own window ends. |
| Date-set publishing | Publishing a newer revision re-plans, in the publisher's transaction, every outstanding unheld job of the calendars using the set: planned ones from their due time, waiting ones from their instant, and signals each definition's planner; an older or equal revision changes nothing, an equal one with other content is refused. Measured at 0.67 s for 47 800 planned jobs of one calendar, the rewrite of each row; accepted, since publishes are rare and correctness needs every planned job re-checked. |
| Expectation declaration | Expectations are `JobPolicy.Expect`, stored with the definition's revision and in its digest only when set, so every process declaring the definition agrees on them; tracked per subject, a key being the definition with the job's subject or alone (owner). Rejected: a separate `work.Expect` registration, which a process declaring the definition without it would contradict, or which would need its own revisions like recurrences. Expectations declared for individual subjects are not offered; per-recurrence expectations through `RecurrenceOptions` remain possible later. |
| Expectation evaluation | Failures, resets and resolutions are written by the transaction that ends the job; deadlines, running attempts and date-set coverage are checked by a monitoring loop in processes that opt in with `work.AddMonitoring()`, over the stored expectations of all definitions; each decision and the incident it opens are one statement over rows locked with `SKIP LOCKED`, in short transactions, so replicas process each deadline once and never wait for an application transaction (owner). The process registry records monitoring processes, and `JobOperations.GetUnmonitoredAsync()` lists definitions with expectations while none is live. Rejected: the definition's own maintenance, which runs only where its handler runs and so misses a total outage of its workers; a recurring framework job, whose schedule limits when a deadline is noticed. |
| Completion deadlines | A deadline's window starts at the previous deadline on an allowed day, so a run completing overnight counts; a day is allowed when the expectation's calendar allows any instant of it, and an uncovered day holds the deadline (owner). The keys expected are the definition's recurrences (code-defined: the definition alone; `ScheduleAsync`: the subject); a definition without recurrences is expected as a whole, and any subject's completion counts. A completion that resolves a missed deadline belongs to it, and the next window starts at that completion. A key is first checked at the first deadline after the loop sees it. Deadlines passed while nothing monitored are processed in order per key; between the first and latest completion after a deadline the rows keep no others, so after more than one unmonitored deadline an incident can open already resolved. Rejected: a window from the day's first allowed instant, which misses runs that complete before the deadline but start the evening before. |
| Expectation state | `job_expectation_states` per key: failures in a row (only with `FailsAtMostInARow`), the key's next deadline with its window start, the first completion in the window, the first and latest completion after a passed deadline the loop has not processed, and whether the row is a definition expected as a whole, which every subject's success also writes (owner). Each row carries its own deadline, so a completion is attributed to the right window however late the loop processes it, and replicas see a processed row as no longer due. A success writes a row once per window, or after a passed unprocessed deadline, and resets failures; incident resolution runs as a separate statement after the row update so it sees incidents the loop committed while the update waited. `Failed` and `TimedOut` count, `Completed` resets, `Cancelled` and `Skipped` neither; retries do not count. Rejected: a waiting flag the loop sets at each deadline, which loses completions committed between a deadline and its processing and after unmonitored deadlines; a last-success time written by every success, which makes one row a lock every completion of a definition without subjects takes, held through application transactions; counting ended rows, which retention deletes and follow-up restarts overwrite; an outcome log folded later, which delays opening and resolution. |
| Incidents | One table `work_incidents`; at most one open incident per (definition, subject, kind, date set), by a partial unique index in that column order with `NULLS NOT DISTINCT`, so a success probes it by its leading columns; resolved incidents are kept 90 days by default (`work.Retention(jobs, runHistory, incidents)`), deleted by the retention job (owner). Only resolutions that resolved a row signal the incident source. Rejected: one incident per missed day, which multiplies incidents during an outage. API: `WorkIncident(Id, Kind, Definition, Subject, DateSet, Job, OpenedAt, ResolvedAt)`, `IncidentOperations.GetIncidentsAsync(openOnly, definition, limit, after)` paged like `GetRunsAsync`. |
| Date-set incidents | Two incident kinds per date set, `DateSetRunningOut` and `DateSetWorkWaiting`, from two conditions evaluated independently and resolved by the monitoring loop (owner). The coverage report's single state gives work waiting precedence, so deriving incidents from it would resolve running out when work starts waiting. Rejected: one incident through both states, which never tells the handler that work started waiting. |
| Incident delivery | The incident row is a framework lease source; every process with `OnIncident` competes for it, one incident at a time by default; opening is delivered before resolution, each recorded in a commit fenced to the lease, and the last commit decides in one locked update whether the row stays due, since a lease end that clears the due time would lose a resolution committed meanwhile (owner). A throwing handler is retried after a capped backoff and never given up. |
| Running attempts check | An attempt held by a lease is checked by its holder's timer, armed from the start of its handler with the running limit of the newest stored revision the process knows; a firing timer opens the incident in one statement that locks the job `FOR SHARE` while the lease is held by its epoch and compares the stored start with the stored limit, so a completion committing meanwhile ends the attempt first. The loop checks only recurring-chain occurrences, a range of `jobs_owned_chain` bounded by `(SELECT clock_timestamp())`, locked `FOR SHARE SKIP LOCKED` (owner). A raised limit re-arms the timer with the time left by the store's clock; maintenance passes read the stored revision and rebuild the definition's source when it is newer, so a lowered limit reaches running attempts within a polling interval even while the process claims nothing. Rejected: an index over `attempt_started_at`, an index entry more for every claim. |
| Telemetry | `ActivitySource` and `Meter` `Corfedo.Work` from the base library, no OpenTelemetry package; instruments and tags as in [monitoring](monitoring.md#telemetry) (owner). Job claims return the due time for lateness, and requests store the requester's W3C trace id (`trace_parent`) that claims return for a span link: an approved change of the job claim's returned columns, not of its selection or indexes. The running gauge is process-local; the oldest-due age and open-incident gauges are store-wide and reported only by monitoring processes. Rejected: a due count per source, a count over the backlog in every process per interval. |
| Exception details | Framework logs describe exceptions by type chain and stack frames without messages, also provider exceptions whose details contain key values; spans record `error.type` and the reason code; `work.Telemetry(t => t.ExceptionDetails())` passes the exception itself, and `Partition()` adds the partition tag (owner, R14, H-3). Rejected: logging whole exceptions and treating logs as the application's pipeline, which H-3 excludes. |
| Expectation API shape (5c) | `Expect.CompletesBy/RunsAtMost/FailsAtMostInARow` return a `JobExpectation` record (`Deadline`, `RunningLimit`, `FailureLimit`), chained with instance methods of the same names; C# forbids a static and an instance method with one signature on one type. Validation at definition creation: time zone through `TimeZoneInfo`, calendar name as `Schedule.Within`, failures at least 0, duration positive, an empty expectation refused. |
| Deadline processing (5c) | The next deadline comes from the .NET calendar evaluator, so a pass locks a definition's due rows `FOR UPDATE SKIP LOCKED`, a pure function (`DeadlineCalculator.Process`) decides each row deadline by deadline, and one statement stores the rows and inserts the incidents, all in one short transaction; each deadline is processed once. A deadline whose window a resolving completion already started after it adds nothing. A day is the local date in the expectation's zone; a calendar with no allowed day within the planning lookahead holds the deadline like an uncovered date. A key first seen with no known previous deadline starts its window when the loop sees it. |
| Expectation revisions and pauses (5c) | Rows store the revision their deadline was computed from; on a new revision the loop moves deadlines to the next one after the window start, placing recorded completions against it. A revision that removes `CompletesBy` clears deadlines and resolves their incidents, one that removes `FailsAtMostInARow` resets failures and resolves its incidents, one that removes `RunsAtMost` resolves its incidents. Paused definitions and paused recurrences are not expected; their keys' deadlines are cleared and open completion incidents resolved; resuming starts with the next deadline (as recommended in the 5c brief). |
| Incident source (5c) | `IncidentSource.Name` = `work:incidents`, lease 30 s, failure backoff exponential 1 s to 5 min, no maximum takeovers; the declared source is replaced with the store's table by an initializer before verification, as job sources are. `OnIncident<T>()` registers handlers; every registered handler is called per event, capacity 1. |
| Telemetry location (5c) | The `Corfedo.Work` ActivitySource, Meter and instruments are internal types of `Abstractions`, visible to the runtime layers and the PostgreSQL provider, since the provider opens and resolves incidents in its own transactions and counts them there; job outcomes are counted by the outcome callback every terminal transition runs, and attempts, spans and lateness by the job handler (owner). A host's options (`Partition`, `ExceptionDetails`) are a DI singleton, so hosts in one process keep their own. |
| Telemetry details (5c) | Counts made inside a transaction (job outcomes, incidents of the ending transaction) are counted again when that transaction rolls back and is applied again, for example after a failing outcome hook; the store has no commit callback, and an accurate count would need one (owner). Tag values are lower snake case (`completed`, `timed_out`, `fails_at_most_in_a_row`). A run span starts its own trace with a link to the request's; a step's `trace_parent` is the activity current when its chain was built, so steps of a recurring chain link to the occurrence's run. Lateness is the process clock at the claim's return minus the stored due time, recorded at zero when clock skew makes it negative. A span of a result without an exception carries the reason code as `error.type`, so reason codes are stable identifiers. |
| Expected-key tracking (5c) | Transactions that create, replace or remove a recurrence or change its copied pause flag (subject pause and resume, maintenance repair) append the key to the insert-only `job_expectation_changes`; each monitoring pass applies and deletes the queued keys, queueing again a key whose row another transaction holds, so a steady pass reads what changed. A definition's revision and pause are reconciled against every key while they differ from `job_definitions.monitored_revision`/`monitored_paused`, recorded by one update guarded by reads without locks of what is left, so rows skipped as locked are taken up by a later pass of any process (owner). Rejected: maintaining the state rows in those transactions, which makes pause and resume wait for open application transactions holding a key's row, contrary to "Pause flag set after a resume"; and bounded pages per pass, which still read every key. Queued keys of definitions without `CompletesBy` are deleted by the loop and by retention. Measurements are in [providers](providers.md). |
| Monitoring wake on key changes (5c) | The transactions that queue an expected key also send a store signal on commit, and the monitoring loop runs a pass when it receives one, so a removed or paused key's `CompletesBy` incident resolves and a new key is seen without waiting for the polling interval (owner). The signal is `work.monitor`, sent only for definitions with `CompletesBy`, whose keys recurrences decide. Rejected: resolving in the write transaction, which needs the state-row locks of the rejected design above; `Plan`, which every ended occurrence also sends. |
| Running-attempt timers (5c) | `RunsAtMost` is checked by the process that holds the attempt: it arms one timer per attempt from the attempt's start and the stored limit and, when it fires while the lease is still held, opens the incident in a statement fenced to the lease; resolution stays in the ending transaction. The monitoring loop keeps only the recurring-chain occurrences, a range scan of `jobs_owned_chain` bounded by the clock read once (owner). The built design is in "Running attempts check". Rejected: the loop reading every held lease of the definition on every pass, 2.7 + 1.8 ms at 5 000 held leases to open nothing. |
| Signals layer (7) | Signals are a layer of their own, used by the framework's layers and by applications: a topic and a key without data, delivered on commit to every process of the application, lossy and without order, with `Resync()` on subscription and reconnection; one listening connection per process, and the provider supplies only the transport (owner). The five framework kinds are the topics `work.due`, `work.plan`, `work.ended`, `work.monitor` and `work.cancel`; provider statements keep signalling from inside the statement through one builder per provider. Rejected: signals inside the store, waking through the outbox, signals carrying data, operations returning their signals as data (a round trip on claims, ends and settlements), a separate transport such as Redis while every transport is the store's own; see [signals](signals.md). |
| Packages | One core package, `Corfedo.Work`, with every layer, plus a package per store provider, the EF Core adapter, the in-memory store and the conformance suite. Separate layer packages saved a signals-only application only Cronos and `Microsoft.Extensions.Hosting.Abstractions`, since the provider implements every store contract (owner). Providers use the core's internals and depend on its exact version. |
| Due times | A record's `DueAt` is when it next needs a run; null means no run is wanted. There is no idle-but-eligible value: a converged reconciliation record has no due time, and requests and invalidations reach every record of the source, so whether a record should converge is the reconciler's decision (owner). Claiming does not clear `DueAt`, so a crashed run is claimable again without a sweep. |
| Transactions | Operations, runs and hooks take `WorkTransaction`, an abstract class with an implicit conversion from any ADO.NET `DbTransaction`, so application code passes its `NpgsqlTransaction` (or, later, `SqlTransaction`) as it is and no provider package repeats the operations (owner). Every conversion of one transaction gives the same handle, which numbers its savepoints. The EF Core adapter's `db.Database.WorkTransaction()` takes a context's transaction, which no conversion can reach since neither type is the framework's; the in-memory store's transactions are handles themselves. The store an operation runs on checks the provider. Rejected: an interface parameter, which C# cannot convert to implicitly; extension methods per provider package, which repeat every transactional operation per provider. |
| Job JSON | A definition names only its argument and result types; their JSON codec is resolved from options the host owns when the definition is registered, as ASP.NET Core does with `ConfigureHttpJsonOptions` (owner). The options start from `JsonSerializerDefaults.General`, which writes what a context without `JsonSourceGenerationOptions` writes, and add the reflection resolver only while `JsonSerializer.IsReflectionEnabledByDefault`, the guarded default ASP.NET Core, System.Text.Json and Microsoft.Extensions.AI use; the trimmer removes it under Native AOT. `WorkBuilder.ConfigureJson` changes the options, `UseJson(resolver)` puts a resolver such as a source-generated context in front of their chain. The host resolves every registered definition's types at startup, so a type missing from an AOT application's context stops startup with the type and the fix named. A definition may take its own `IJobArgs<TArgs>`/`IJobResults<TResult>` for versioned arguments or another format, which wins over the host's options. Rejected: the codec on the definition, which a static value created before dependency injection cannot take from the host; a JSON source generator; a delegate `AddJob` form. |
| Request defaults | A definition's revision defaults to 1 and a request's schedule to `Schedule.Now` (owner). A policy change without a revision bump is still refused at startup, so the default hides nothing that fails silently. Recurrences (`ScheduleAsync`, `AddRecurring`) and `RequestChainAsync(tx, chain, schedule)` keep their explicit schedule. |
| Requests without a transaction | `JobOperations.RequestAsync(definition, args, ...)` without a transaction commits in the store's own transaction and signals claimers after that commit, following the transaction and non-transaction overloads of leases and reconciliation (owner). The store runs its transactional request path in a READ COMMITTED transaction of its own. Only requests have it; other operations get one when a need appears. The transactional form stays the documented default. Rejected: expression-based requests (rename-fragile, not AOT-compatible), string function names (no compile-time link), requests by handler type (request-only processes would reference handlers), a separate name such as `RequestNowAsync`. |
| Out of scope | Message delivery, process-local timers, workflow engines beyond chains, dashboards, AI assistance, notification transports, stored handler log lines. |
| Native AOT and EF Core | `Corfedo.Work.EntityFrameworkCore` does not support Native AOT, and the AOT smoke application leaves it out; its own code passes the trimming and AOT analyzers. EF Core rejects runtime model building under Native AOT and needs a compiled model, and EF Core and its Npgsql provider report trimming and AOT warnings of their own, including on the `DbContext` constructor. The other packages stay Native AOT-compatible (owner decision). |
